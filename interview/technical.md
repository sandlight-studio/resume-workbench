# 技术面速答（虚构示例）

## 1. 如何设计幂等接口？

先定义“同一次业务动作”的稳定键，再决定由哪一层保证唯一。

- 接入层保存请求键和原始载荷，重复请求返回已有结果。
- 数据库用唯一约束兜底，不把正确性只放在 Redis 上。
- 消费端以状态机推进；只有允许的前置状态才能进入下一状态。
- 对失败区分可重试和不可重试，避免永久错误无限循环。

张三的虚构例子见[幂等回调故事](story-idempotent-callback.md)。

## 2. 缓存与数据库如何保持一致？

默认数据库是真实来源。写入成功后删除缓存，读取未命中时回源；热点键重建使用短租约，
但租约失效也不能破坏数据库约束。需要更强一致性时，应说明延迟双删、订阅变更日志或
直接绕过缓存各自解决什么问题，而不是给出一个万能方案。

## 3. 消息一定不会丢吗？

不能只回答“开启持久化”。示例链路采用：

1. 业务事务内写事件记录；
2. 事务提交后发送消息；
3. 定时扫描未发送事件作为兜底；
4. 消费端幂等；
5. 达到重试上限后进入可查询终态。

这是至少一次投递，不是假装实现不存在的“绝对不丢、绝对不重”。

## 4. 线程池怎么定参数？

先区分 CPU 密集和 I/O 密集，再用到达率、平均处理时间和可接受队列等待估算容量。
上线后看活跃线程、队列长度、拒绝次数和任务耗时。示例平台使用有界队列和显式拒绝，
因为无限堆积只是把过载推迟成内存事故。

## 5. 数据库连接池耗尽怎么排查？

确认是连接泄漏、慢 SQL、长事务还是并发突然上升：同时查看池等待指标、数据库活动会话、
慢查询、线程转储和变更记录。不要先盲目调大连接池；这可能把压力直接推给数据库。

## 6. 如何讲系统设计题？

按约束推进：用户规模与峰值、核心用例、一致性目标、数据模型、接口、读写链路、失败模式、
容量保护、可观测性。每一步说明假设，面试官修改假设时再调整方案。
